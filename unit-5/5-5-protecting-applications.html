5.5 • Protecting Applications

Secure by Design

Secure by design means security is considered during the design and development of an application rather than being added only after the application is completed. Security should be considered throughout the development process.

Big idea

Applications should be secure from the beginning, not patched after the fact.

Instead of building an application, finding security problems, and then trying to fix them, developers should think about security from the beginning. They should plan, design securely, develop carefully, test, deploy, monitor, and update the application over time.

Secure by design means security is considered during the design and development of an application rather than being added only after the application is completed.

Security should be considered throughout the development process:

Plan → Design securely → Develop → Test → Deploy → Monitor → Update

The AP framework identifies three important principles: customer security, company responsibility, and leadership and commitment.

Security by default means applications should begin with secure settings rather than requiring users to manually enable every security feature.

Examples might include strong authentication, secure communication, unnecessary services disabled, and restrictive permissions by default.

The basic principle is: The safest reasonable configuration should be the default configuration.

One of the most important application-security techniques is input sanitization.

Whenever a program accepts information from a user, that information should be treated as untrusted.

Examples: username, password, search query, comment, file name, URL, or form submission.

The application should check whether the input is valid before processing it.

Without proper input validation, attackers may attempt to provide unexpected input that changes how the application behaves.

The AP framework connects improper input handling to attacks such as SQL injection, cross-site scripting, and directory traversal.

Suppose a website expects an age of 15. The application should determine whether the submitted value is actually an appropriate age value. It should not blindly trust <script>...</script> or ../../../private/file or unexpected database commands.

A useful rule for developers is: Never trust user input.

This does not mean users are automatically malicious. It means the application should assume input could be incorrect, unexpected, malicious, or manipulated.

Core rules

  • Build security in early.
  • Use secure defaults.
  • Validate every input.
  • Never trust user-provided data.
  • Monitor and update after deployment.

Practice question

If a form accepts a file name and passes it directly to a file handler, what could happen if the input is not validated?

My notes

Key takeaways

  • Security should be built into the application lifecycle from the beginning.
  • Secure by default means the safest reasonable configuration is used automatically.
  • Input sanitization and validation reduce the risk of SQL injection, XSS, and directory traversal.
  • Developers should assume user input may be bad, unexpected, or malicious.

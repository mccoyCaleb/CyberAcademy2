3.8 • Logs Part 2

Advanced Log Analysis

The first logs lesson taught how to read one entry. This lesson goes further and shows how analysts sort through large amounts of ordinary activity to find patterns that may indicate suspicious behavior.

ProgressPattern analysis

Big idea

Normal activity is noisy. Suspicious behavior becomes clear when you compare patterns.

Real cybersecurity work is not about identifying a single "attack" word in a log. It is about understanding the normal baseline and then noticing repeated events, unusual commands, suspicious URLs, failed logins, privilege changes, or access attempts that deserve investigation.

Baseline

Know the normal

Before you can call something suspicious, you need to know what ordinary activity looks like on the system.

Patterns

Look for repetition

One strange event may be harmless. Several related events in a short period are much more meaningful.

Context

Ask the right questions

Analysts ask who, when, what, which source, and what happened around the event before deciding if it is a problem.

1. Logs are not all the same

Different systems produce different log types. A single security investigation may require information from several sources:

  • Web server logs: HTTP methods, paths, status codes, and suspicious URLs.
  • Linux system logs: service activity, package updates, scheduled tasks, and administrative actions.
  • Authentication logs: logins, failed passwords, SSH access, and privilege changes.
  • Network logs: connections, ports, firewall rules, DNS, and ARP behavior.

A server might generate thousands of legitimate events every day. A system may log:

User logs in → opens a website → loads CSS → loads JavaScript → downloads an image → checks email → runs software updates → logs out

All of those can appear in logs. This means: a technical-looking log entry does not automatically mean suspicious activity.

For example, something like sudo: jprice : USER=root ; COMMAND=/usr/bin/apt update may look alarming, but it could simply be a user running a legitimate software update.

Consider a sequence where a user runs:

sudo
less /var/log/syslog
apt-get update
systemctl status apache2
ufw status verbose

These are normal administrative and troubleshooting actions. A student or administrator may review logs, check the firewall, inspect Apache, or update packages. These actions only become suspicious when the surrounding context does not make sense.

Context matters. If the user is expected to manage the system, the event is normal. If the user is not authorized, or the behavior happens at odd times with other suspicious events, then the analyst would investigate further.

ARP is used to map an IP address to a MAC address on a local network. This is important because a device may send a request like:

Who has 192.168.1.13?
192.168.1.13 is-at 00:01:5e:00:fc:16

If the same IP later appears with a different MAC address, that could be normal or it could be suspicious. A device may have changed, DHCP may have assigned a new address, or a virtual machine may have moved.

That means: a changed ARP mapping does not automatically mean ARP poisoning. But it is a pattern worth checking, especially if multiple IPs suddenly map to the same MAC address.

Web logs can show suspicious input patterns such as:

GET /search?q=<script>...</script>
GET /download?file=../../etc/passwd

These patterns may indicate XSS or directory traversal attempts. But the presence of suspicious text alone does not prove a successful attack. A server might return 400, 403, or even 200 for a request that was attempted. The analyst still needs to check the response, the application behavior, and related logs.

The key distinction is between an attempt and a successful compromise.

One failed login is often not enough to conclude anything. But repeated failures from the same source are much more interesting:

Failed login for invalid user admin
Failed login for invalid user root
Failed login for invalid user test
Failed login for invalid user guest

This pattern is consistent with automated password guessing or account enumeration. The source is the same, the events are close together, and the usernames are common. That is a stronger signal than a single failed login.

Again, the key word is consistent. It is evidence for investigation, not proof of compromise.

SSH and FTP logs can show the same pattern when an attacker is testing accounts or guessing credentials.

Failed login for invalid user admin from 203.0.113.25
Failed login for invalid user root from 203.0.113.25
Failed login for invalid user guest from 203.0.113.25

When the same IP tries many usernames very quickly, analysts should ask whether this is automated reconnaissance, a brute-force attempt, or a normal maintenance action from an approved source.

On the other hand, a successful SSH login followed by a normal administrative command can also be harmless. The analyst must follow the sequence and determine whether the activity matches expected behavior.

Commands like:

sudo
USER=root
uid=0
COMMAND=/usr/bin/apt update

should be considered carefully. Root access is not automatically malicious, but it deserves attention.

Analysts should ask:

  • Who used it?
  • When did it happen?
  • What command did they run?
  • Was that user expected to have admin rights?
  • Did the command match normal behavior for that account?

Advanced log analysis is about moving from:

"What does this one line mean?"
→ "What story do these events tell together?"

A single 404 does not mean an attack. A single 401 does not mean an attack. A single 500 does not mean an attack. But a burst of failed requests, suspicious paths, unusual commands, or repeated authentication activity from one source may be a meaningful event sequence.

The strongest analysis combines:

  • IP addresses
  • Usernames
  • Timestamps
  • HTTP methods and paths
  • Status codes
  • Authentication events
  • Process or command activity
  • Context within the system

2. Patterns that deserve attention

Common advanced indicators

  • Repeated failed logins: same source, many usernames, tight time intervals.
  • Suspicious URLs: ../, ../../, %2e%2e%2f, <script>.
  • Unexpected ARP changes: IP address changes from one MAC to another without explanation.
  • Large numbers of 404s: especially for paths like /admin, /backup, /config, and /.env.
  • Unexpected privilege use: commands that use sudo, su, or USER=root.

Which statement best reflects the goal of advanced log analysis?

Correct: Good log analysis combines evidence from several events and asks what the broader pattern means before drawing conclusions.

Checklist

Remember

  • Normal activity can look technical.
  • Suspicious activity often becomes clear only when a sequence is analyzed.
  • Attack patterns are evidence for investigation, not automatic proof.
  • Timeline-building is one of the strongest tools in cyber analysis.

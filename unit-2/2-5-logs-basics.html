2.5 • Logs Basics

HTTP Requests, Status Codes, and Server Logs

HTTP logs record requests, responses, and other events. This section teaches how to read HTTP methods, status codes, and server log entries, then connect individual events into timelines and patterns without jumping to unsupported conclusions.

ProgressWeb log analysis

Big idea

One log line is an event. A sequence becomes evidence.

HTTP (Hypertext Transfer Protocol) allows clients, such as web browsers, applications, and other devices, to communicate with web servers. When you visit a website, your browser sends an HTTP request to a server. The server processes that request and sends back an HTTP response.

Client → HTTP Request → Server → HTTP Response → Client
Requests

What the client asks for

An HTTP request can contain a method, path, HTTP version, headers, and a body when data is being sent to the server.

Responses

How the server responds

A status code describes how the server handled the request, from a successful response to a client error or server problem.

Analysis

How analysts investigate

Analysts connect who, when, what, result, how, pattern, and context before deciding what an event means.

1. Understanding HTTP requests

An HTTP request can contain several important pieces of information:

  • Method: What the client wants to do.
  • Path: Which resource the client wants to access.
  • HTTP version: Which version of HTTP is being used.
  • Headers: Additional information about the request.
  • Body: Data being sent to the server, when applicable.

GET requests are used to retrieve information from a server.

Example: GET /users HTTP/1.1

The client is asking the server to return the resource at /users. GET is one of the most common HTTP methods because browsers use it constantly when loading websites. When you visit https://example.com/, your browser will typically send a GET request for the page.

The browser may then make additional GET requests for images, CSS files, JavaScript, fonts, videos, and other resources.

Characteristics: GET is intended to retrieve information rather than modify server data, so it is safe. Repeating the same GET request should have the same intended effect on the server, so it is idempotent. GET responses can generally be cached when the server's caching rules allow it.

GET requests can include information in the URL using a query string: GET /search?q=cybersecurity HTTP/1.1. Here, /search is the path and ?q=cybersecurity is the query string. The server can use the q parameter to determine what the client is searching for.

Cybersecurity consideration: Sensitive information should generally not be placed in a GET URL. Passwords in URLs are dangerous because URLs can potentially appear in browser history, server logs, proxy logs, monitoring systems, and analytics systems.

Common responses: 200 OK, 304 Not Modified, 400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found, and 500 Internal Server Error.

POST is commonly used to send data to a server for processing.

Example: POST /users HTTP/1.1

The request body could contain:

username=jprice
email=jprice@example.com

POST is commonly used for creating accounts, submitting forms, sending messages, uploading information, creating database records, and sending API requests.

POST is not safe because it can modify the server's state. It is not inherently idempotent: if a website uses POST to create an order, sending the request twice could potentially create two orders. POST is not cacheable by default.

Common responses: 200 OK, 201 Created, 202 Accepted, 400 Bad Request, 401 Unauthorized, 403 Forbidden, 409 Conflict, and 500 Internal Server Error.

PUT is used to replace the current representation of a resource with the information supplied by the client.

PUT /users/123 HTTP/1.1

{
  "name": "John Price",
  "email": "john@example.com"
}

PUT is not safe, idempotent, and generally not cacheable. If the same PUT request is sent multiple times, the intended final state should remain the same.

PATCH modifies only part of an existing resource.

PATCH /users/123 HTTP/1.1

{ "email": "newemail@example.com" }

Instead of replacing all of the user's information, the server only changes the email address. PATCH is not safe, not inherently idempotent, and generally not cacheable. Whether a particular PATCH operation is idempotent depends on what the operation actually does.

DELETE requests the removal of a resource: DELETE /users/123 HTTP/1.1. DELETE is not safe, idempotent, and generally not cacheable. Repeating a DELETE request does not normally cause additional deletions after the resource is already gone.

Cybersecurity consideration: DELETE requests can be important during security investigations because unauthorized users may attempt to delete accounts, files, database records, backups, logs, or configuration information.

HEAD works similarly to GET, but the server does not return the response body. A client may receive information such as Content-Type, Content-Length, and Last-Modified without receiving the actual HTML page. HEAD is useful when a client wants to determine information about a resource without downloading the resource itself.

OPTIONS asks the server which communication methods or options are supported. For example, OPTIONS /api/users HTTP/1.1 might receive Allow: GET, POST, PUT, DELETE. OPTIONS is also important in CORS, where browsers can perform a preflight request before certain cross-origin requests.

CONNECT asks a proxy to create a tunnel to another server: CONNECT www.example.com:443 HTTP/1.1. This is commonly associated with HTTPS connections through a proxy. A successful response might be 200 Connection Established. CONNECT establishes a tunnel; HTTPS/TLS provides the encryption and authentication for HTTPS traffic.

TRACE is primarily a diagnostic method. The server can return information about the request it received. TRACE can help diagnose how requests are being handled by network components. It is commonly disabled on production servers because of security concerns in certain configurations.

HTTP status codes are three-digit numbers returned by the server. They are divided into five categories:

1xx → Informational
2xx → Success
3xx → Redirection
4xx → Client/request error
5xx → Server error

1xx — Informational: The server has received the request and communication is continuing. 100 Continue tells the client it can continue sending the request. 101 Switching Protocols means the server agrees to switch to another protocol. 103 Early Hints sends preliminary information before the final response.

2xx — Success: 200 OK means the request succeeded. 201 Created means a new resource was successfully created, commonly after POST. 202 Accepted means the request was accepted but processing may not be finished. 204 No Content means the request succeeded but there is no response body.

3xx — Redirection: 301 Moved Permanently means the resource has permanently moved. 302 Found means the resource is temporarily available somewhere else. 304 Not Modified means the resource has not changed, so the client can use its cached copy. 307 Temporary Redirect and 308 Permanent Redirect preserve the request method while redirecting.

4xx — Client/request errors: 400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found, 405 Method Not Allowed, 408 Request Timeout, 409 Conflict, and 429 Too Many Requests. A 405 means the resource exists but the HTTP method is not allowed. A 429 is commonly associated with rate limiting.

5xx — Server errors: 500 Internal Server Error means the server encountered an unexpected problem. 502 Bad Gateway means a gateway or proxy received an invalid response from another server. 503 Service Unavailable means the service is temporarily unable to handle the request. 504 Gateway Timeout means a gateway or proxy did not receive a response from another server in time.

Web servers create logs that record requests and other events. These logs are extremely useful in cybersecurity because they allow analysts to reconstruct what happened.

29 - 192.168.1.50 - jprice [10/Nov/2025:09:05:30 -0500] "GET / HTTP/1.1" 200 4231 "-" "Mozilla/5.0 (Ubuntu)"

Request identifier: 29 is a field included in this particular log format. It may represent a request or record identifier. The exact meaning depends on how the server's logging system is configured.

Source IP address: 192.168.1.50 is the IP address associated with the client making the request. We should not automatically say that a specific person made the request. Proxies, VPNs, NAT, and compromised devices can affect which IP address appears in a log. Treat the IP as evidence about the network source, not automatic proof of a person's identity.

Identity: jprice represents an identity or username according to the logging configuration. It should not automatically be interpreted as the device name. If the server associates requests with authenticated users, it might represent the account that made the request. An analyst should learn how the server defines the field.

Timestamp: [10/Nov/2025:09:05:30 -0500] gives the date, time, and offset. Timestamps are extremely important when investigating an incident because an analyst can search the logs around the reported time and build a sequence of events.

Method and path: GET / means the client requested information at the root path. In many web applications, this corresponds to the homepage. HTTP/1.1 identifies the HTTP version.

Status and response size: 200 means the server successfully processed the request. 4231 commonly represents the response size, approximately 4,231 bytes in this example, although the exact interpretation depends on the logging configuration.

Referrer: - indicates that no referrer information was recorded. A referrer can sometimes tell the server which page led to the current request.

User-Agent: Mozilla/5.0 (Ubuntu) provides information about the software making the request, such as a browser, operating system, or client software. It is not definitive proof because a program can intentionally send a User-Agent that pretends to be a browser.

Overall interpretation: At 9:05:30 AM on November 10, 2025, the server recorded a GET request for the website's root path from source IP 192.168.1.50, associated with identity jprice. The server returned a 200 OK response. This is consistent with a normal request for a website's homepage, but one line alone does not prove that it was legitimate.

29 - 192.168.1.50 - jprice [10/Nov/2025:09:05:30 -0500] "GET / HTTP/1.1" 200 4231 "-" "Mozilla/5.0 (Ubuntu)"
30 - 192.168.1.50 - jprice [10/Nov/2025:09:05:31 -0500] "GET /images/banner.jpg HTTP/1.1" 200 3087 "-" "Mozilla/5.0 (Ubuntu)"

The second request comes one second after the first. It uses the same source IP and identity, requests /images/banner.jpg, receives a 200 response, and returns approximately 3,087 bytes.

Why might this happen immediately after GET /? A webpage is made up of many resources. The browser requests the HTML, reads it, finds an image, then requests the image. It may then request CSS and JavaScript.

GET / → HTML page → browser reads HTML → GET /images/banner.jpg → GET /style.css → GET /script.js

Several GET requests within a few seconds can be completely normal. An analyst should understand what the application normally does before treating a high number of requests as malicious.

10.20.30.40 - - [10/Nov/2025:09:15:01 -0500] "GET /admin HTTP/1.1" 404 512 "-" "python-requests"
10.20.30.40 - - [10/Nov/2025:09:15:02 -0500] "GET /backup HTTP/1.1" 404 512 "-" "python-requests"
10.20.30.40 - - [10/Nov/2025:09:15:03 -0500] "GET /config HTTP/1.1" 404 512 "-" "python-requests"
10.20.30.40 - - [10/Nov/2025:09:15:04 -0500] "GET /.env HTTP/1.1" 404 512 "-" "python-requests"

Every request comes from 10.20.30.40, and there is exactly one second between requests. That regular timing may be consistent with automated activity, but timing alone does not prove malicious activity.

The paths /admin, /backup, /config, and /.env could potentially contain administrative or configuration information on some systems. Requesting them does not prove that they exist or that anyone successfully accessed them.

Every response is 404 Not Found, so the server did not report that these resources were found. We should say that the client requested these paths and the server returned 404 responses. We should not say that an attacker accessed configuration files.

The User-Agent python-requests is a clue that the traffic may have been generated programmatically, but User-Agent values can be changed. The overall pattern could be consistent with automated reconnaissance or directory/file scanning. An authorized vulnerability scanner could create the same traffic.

Next, investigate whether the IP is expected, whether the same source made successful 200 or 302 requests, whether authentication events occurred, whether files were actually accessed, and whether the scan was authorized.

Repeated requests such as these return 401 Unauthorized:

192.168.1.80 - - [10/Nov/2025:10:00:01] "GET /admin HTTP/1.1" 401
192.168.1.80 - - [10/Nov/2025:10:00:03] "GET /admin HTTP/1.1" 401
192.168.1.80 - - [10/Nov/2025:10:00:05] "GET /admin HTTP/1.1" 401

This generally indicates that authentication is required or that supplied authentication credentials were not accepted. An analyst might investigate repeated authentication attempts.

Now consider: 192.168.1.80 - jprice [10:05:01] "GET /admin HTTP/1.1" 403. A 403 Forbidden response means the server understood the request but refused access. This generally points more toward an authorization or access-control issue.

401 → Authentication → “Who are you?”
403 → Authorization → “You are not allowed to do this.”

The exact behavior depends on the application, so analysts should also examine its documentation and configuration.

192.168.1.50 - jprice [10:20:00] "POST /login HTTP/1.1" 200
192.168.1.50 - jprice [10:20:03] "GET /dashboard HTTP/1.1" 200
192.168.1.50 - jprice [10:20:05] "GET /admin/users HTTP/1.1" 403
192.168.1.50 - jprice [10:20:07] "DELETE /users/123 HTTP/1.1" 403

POST /login → 200 means the login request was processed successfully according to the HTTP response, although authentication logs should be checked to determine exactly what happened.

GET /dashboard → 200 means the same recorded identity accessed the dashboard successfully.

GET /admin/users → 403 means the client attempted to access an administrative user-management resource, but the server refused access.

DELETE /users/123 → 403 means the client attempted a DELETE request against a user resource, but the server refused it.

The server appears to have prevented the requested administrative actions. The sequence demonstrates why authorization controls and logging are important: a login occurred, a normal resource was accessed, a restricted resource was attempted, and a restricted modification was attempted and refused. Additional logs are needed to determine whether the activity was legitimate, accidental, or unauthorized.

192.168.1.25 - - [10:30:01] "GET /api/users HTTP/1.1" 500
192.168.1.25 - - [10:30:02] "GET /api/users HTTP/1.1" 500
192.168.1.25 - - [10:30:03] "GET /api/users HTTP/1.1" 500
192.168.1.25 - - [10:30:04] "GET /api/users HTTP/1.1" 503

A server that repeatedly fails may have crashed, lost database access, become overloaded, entered maintenance, lost a backend service, or encountered a software bug. A 5xx response does not automatically mean an attack occurred.

Compare HTTP logs with application logs, database logs, server resource usage, authentication logs, network monitoring, and system alerts. This can show whether errors came from an attack, an outage, a software problem, or something else.

45 - 10.0.0.25 - alex [11:00:01] "GET / HTTP/1.1" 200 4200 "-" "Mozilla/5.0"
46 - 10.0.0.25 - alex [11:00:01] "GET /style.css HTTP/1.1" 200 1800 "-" "Mozilla/5.0"
47 - 10.0.0.25 - alex [11:00:02] "GET /images/logo.png HTTP/1.1" 200 2500 "-" "Mozilla/5.0"
48 - 10.0.0.25 - alex [11:00:05] "POST /login HTTP/1.1" 401 600 "-" "Mozilla/5.0"
49 - 10.0.0.25 - alex [11:00:07] "POST /login HTTP/1.1" 401 600 "-" "Mozilla/5.0"
50 - 10.0.0.25 - alex [11:00:09] "POST /login HTTP/1.1" 200 1200 "-" "Mozilla/5.0"
51 - 10.0.0.25 - alex [11:00:10] "GET /dashboard HTTP/1.1" 200 6000 "-" "Mozilla/5.0"

11:00:01 — Website loaded: GET / → 200. The client requested the homepage and the server returned it.

11:00:01 — CSS loaded: GET /style.css → 200. 11:00:02 — Image loaded: GET /images/logo.png → 200. These requests are consistent with normal webpage loading.

11:00:05 — Failed login: POST /login → 401. 11:00:07 — Another failed login: POST /login → 401. The login attempts were not authenticated successfully according to the HTTP responses.

11:00:09 — Successful login response: POST /login → 200. 11:00:10 — Dashboard accessed: GET /dashboard → 200.

Website loaded → resources loaded → login attempted → login failed → login attempted again → login succeeded → dashboard accessed

Timestamps and status codes let an analyst construct a reasonable sequence, but the logs alone do not tell us why the first two logins failed or whether the successful login was legitimate. Additional evidence is needed.

When examining HTTP logs, do not simply look for one “bad” status code. Ask:

  • Who? What IP address is associated with the request? What user or identity is recorded?
  • When? When did the request happen? Are there multiple requests close together?
  • What? What HTTP method was used? What resource was requested?
  • Result? What status code did the server return?
  • How? What User-Agent or other request information was recorded?
  • Pattern? Does the activity form a recognizable pattern?
  • Context? Is the activity expected, such as a security team running an authorized vulnerability scanner?

Possible patterns include many 401s, which may indicate repeated authentication failures; many 404s for unusual paths, which may indicate scanning or reconnaissance; and many 500s, which may indicate an application or server problem.

The goal of log analysis is not to look at one line and immediately decide that something is an attack.

Individual Event → Multiple Events → Timeline → Pattern → Context → Investigation

A single 404 does not mean an attack. A single 401 does not mean an attack. A single 500 does not mean an attack. A large number of events, their timing, their targets, their sources, and their relationship to other system activity provide much more useful evidence.

Practice the analyst mindset

When a log looks unusual, describe exactly what the log supports before adding an interpretation. For example: “The client requested several potentially sensitive paths from the same source at one-second intervals, and each request returned 404.” Then identify what evidence you would investigate next.

My notes

Quick memory guide

  • GET → retrieve information
  • POST → submit or process data
  • PUT → replace a resource
  • PATCH → partially modify a resource
  • DELETE → remove a resource
  • 401 → authentication is required or failed
  • 403 → access is forbidden
  • 404 → resource was not found
  • 5xx → server-side problem

Investigation checklist

Evidence matters

A User-Agent reports what the client claims. An IP identifies a network source, not automatically a person. A status code describes the response, not the entire story.

Key takeaways

  • HTTP methods describe what a client wants to do, while status codes describe how the server handled the request.
  • Server logs provide useful evidence about sources, identities, times, paths, methods, results, response sizes, referrers, and User-Agents.
  • Normal browsing can create many requests, and unusual requests do not prove that an attack succeeded.
  • Analysts should connect events into timelines and patterns, then add context before reaching conclusions.
  • A 404, 401, or 500 by itself does not prove an attack.
